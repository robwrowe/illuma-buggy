# E90C Packets - Multi-Zone Color (Solid / Flash / Chase)

Lights the five LED zones (Center, TopRight, BottomRight, BottomLeft, TopLeft) using either
independently-assigned colors in a chase animation (UL → BL → BR → UR → Center), or a
solid/flash pattern where TL/BL/BR share a role, TR carries a separate role, and Center often
sits at a third role. Which family is in play is selected by the **per-zone mask bits**, not
byte 14 as previously theorized (see Revision History).

Note: **every confirmed real-world packet (chase and flash/solid alike) is 16 bytes as
captured** — 18 doc bytes with the `83 01` prefix restored, doc byte 17 is the last byte. There
is no length difference between families; see the Revision History and Bytes 15-17 section for
the retraction of a prior "extra tail byte" finding that was based on a corrupted capture batch.


**Numbering convention note (important — this doc and the app's rule config disagree by 2).**
All byte numbers in this doc — in both diagrams above and every "Byte NN" reference in the
prose below — count from the start of the `83 01` prefix (byte 0 = `83`, byte 1 = `01`, byte 5 =
`E1`/`E2`, byte 7 = timing, byte 9 = first zone byte). This matches the doc's own established
convention and its cross-references to `E9-05.md`. **The `mbMapping.rules` JSON in the app
config counts from the `E1`/`E2` byte instead (byte 0 = `E1`, byte 5 = timing, byte 7 = first
zone byte)** — confirmed against the working `e9-0e_five-color_strobe_directional` rule, whose
`offset: 13` match condition lands on E9 0E's pattern-shape-seed byte only under that
convention. **To convert a byte number from this doc into a rule-config `offset`, subtract 2.**
The chase-family byte table below states offsets in "doc numbering (subtract 2 for rule
offset)" form to make this explicit at each field.

Raw lab captures for this opcode typically start at the OP code (`E9 0C ...`) without the
`8301 <E1|E2> 00` prefix, and the JSON export tool's `bytes` field always starts at `E1`/`E2`
(never `83 01`) — so when reading a raw capture against this doc, add 2 to whatever index you
count in the capture to get this doc's byte number.

**Retracted: all E9 0C packets are the same length.** A prior revision claimed flash/solid-family
packets carried an extra tail byte (17 bytes as captured / 19 doc bytes) not present in chase
packets. This was wrong — it was built from a capture batch
(`wand-lab-log-1784773152359.json`'s byte-14 sweep) that turned out to contain a corrupted or
duplicated byte in every single sample: all 8 samples in that sweep showed a constant `0xFC` at
doc-byte 15 regardless of what was actually being swept, which should have been the giveaway that
something was wrong with the capture rather than a real field. Rob supplied a fresh batch of
confirmed-working real-world show packets, all 16 bytes as captured (18 doc bytes) — chase and
flash/solid alike — which settles it: **there is no length difference between families.** The
modifier lives at doc-byte 14 in both, immediately followed by the same 3-byte tail at doc-bytes
15-17. The "confirmed inert extra tail byte" claim and its dedicated sweep from two revisions ago
are retracted along with it — that sweep necessarily inherited the same corrupted-capture problem
since it used the same batch as its baseline template.

- Prior revision: original chase/solid split based on byte 14 (`0x30` vs `0xF0`) and the

## Byte Details

### Byte 07 - Timing

Same bit layout as [timing byte detail](../timing-byte.md). **Confirmed reliable in both solid
mode and chase mode**, using the same `1.5×tval` (scaler=0) / `3.0×tval` (scaler=1) formula
documented for E9 05/09/0E.

- `0x01` (t=1, scaler=0, fade=0) → predicted on-time `1.6×1=1.6s`, matches observed
  "Solid white for 1.5s" closely (solid-mode confirmation, prior revision).

**Chase-mode confirmed via a controlled sweep** (`wand-lab-log-1784773152359.json`, 8 samples,
zone colors/byte-14/tail all held constant at `B2A4B5B2B5` / `0x30` / `7B7DB0`, only `tval`
varied 1→15 at scaler=0):

| `tval` | predicted (`1.5×tval`) | observed on-time | diff |
| --- | --- | --- | --- |
| 1 | 1.5s | ~1.5s | 0.0s |
| 3 | 4.5s | ~4.5s | 0.0s |
| 5 | 7.5s | ~7.5–8.0s | ~0.1s |
| 7 | 10.5s | ~11.0s | +0.5s |
| 9 | 13.5s | ~14.0s | +0.5s |
| 11 | 16.5s | ~17.0s | +0.5s |
| 13 | 19.5s | ~20.0s | +0.5s |
| 15 | 22.5s | ~23.0s | +0.5s |

Linear regression on this data gives a best-fit slope of `1.54` and near-zero intercept —
`1.5×tval` is confirmed as the correct chase-mode formula, no separate constant needed. The
**prior revision's "no monotonic relationship" finding is retracted** — that sweep varied tail
and byte-14 values inconsistently across samples alongside `tval`, which masked the real
relationship. This sweep held everything else fixed and the fit is clean (max deviation ~0.5s
across the full range, consistent with your stopwatch/observation precision, not decode error).

One data point at `tval=4, scaler=1` (byte `0x64`) also fits: predicted `3.0×4=12.0s`, observed
"~13s on time, fade out" — matches once the ~1.0s fade (see fade-bits note below) is added on
top, confirming the scaler=1 multiplier carries over too.

**Per-cycle (per-zone-step) dwell time is not exactly `on_time ÷ cycles`.** Dividing observed
on-time by counted cycles gives a value that drifts from ~1.9s (at tval=5) down toward ~1.6s
(at tval=15) rather than a flat 1.5s. This is expected given Rob's noted counting methodology
(only full repeats counted, so a partial cycle at start/end isn't reflected) — not a sign the
per-step formula is wrong. Treat `on_time = 1.5×tval` (or `3.0×tval` for scaler=1) as the
reliable figure; back-calculate per-step dwell as `on_time ÷ 5` (5 zones) if a rule engine needs
a discrete step duration, rather than trusting raw `on_time ÷ observed_cycle_count`.

**Bit 7 (`always_on`) still confirmed meaningful** independent of the rest of the byte — from
the previous revision's dataset, every `always_on=1` sample ran well past its nominal cycle
count without self-terminating (90+ seconds, one case ~3 min 49 sec), while every
`always_on=0` sample stopped at a bounded total time. Not retested in this sweep (which only
used `always_on=0`), but nothing here contradicts it.

**Fade bits — retracted the earlier "2x discrepancy" caution.** That flag was based on a sample
that wasn't properly isolated. With a controlled sample (`0x64` → `fade_bits=2`, scaler=1,
tval=4): predicted on-time `3.0×4=12.0s` + predicted fade `fade_bits×0.5s=1.0s` = `13.0s` total,
matching the observed "~13s on time, fade out" almost exactly. `fade_bits × 0.5s` is confirmed
reliable in chase mode, consistent with E9 05/0E.

### Byte 08 - Length/Marker

Constant `0x0F` across every sample collected so far (22/22, old + new lab log combined).
Likely a fixed marker or length byte, consistent with the same constant appearing in E9 0E.
Not yet tested with other values.

### Bytes 09-13 - Per-Zone Color

Five consecutive bytes, one per LED zone, in the order **TopLeft, BottomLeft, BottomRight,
TopRight, Center** — same zone ordering already confirmed for E9 09.

**Confirmed:** each byte follows the same mask+color split as
[E9 05 byte 09](./e9-05.md#byte-09---mask--color) (top 3 bits = mask, bottom 5 bits = color
index into the [Color and Mask Palette](../color-and-mask-palette.md)).

**Retracted: "mask is always `0b101`."** The prior revision's mask-anomaly theory was based on
a sample set that happened to be all-chase. The expanded dataset shows mask bits vary
meaningfully and are the actual family selector — see the table below.

**Confirmed — mask pattern is the family selector, not byte 14:**

| Mask pattern (TL BL BR TR C) | Family | Sample count | Example note |
| --- | --- | --- | --- |
| `101 101 101 101 101` | **Chase** — 5 independent zone colors, TL→BL→BR→TR→C animation | 9/9 | "Five color chase... UL > BL > BR > UR > Center" |
| `010 010 010 111 111` | **Flash family A** | 2/2 | "orange blink/slow strobe" |
| `010 010 010 111 000` | **Flash/solid family B** | 6/6 | "Solid white for 1.5s", "lightning style flash", "cuts on, slowly fades out" |
| `010 010 010 100 000` | **Flash/solid family C** (new, 1 sample) | 1/1 | "Purple cuts on, fades out over ~0.25s" |

Within families B and C, TL/BL always share the same mask (`010`), BR also carries `010` in
both, and only TR (and sometimes C) differ — worth testing whether TR's mask value itself
selects a further sub-behavior (see Suggested Lab Tests).

**Confirmed from lab data (chase family):** color-index decode cross-checked against repeat
counts and named colors in observation notes across 9 independent samples (expanded from the
prior revision's 4) — all matched, including three new samples from the 2026-07 sweep:

| Zone bytes (TL BL BR TR C) | Decoded colors | Observed note |
| --- | --- | --- |
| `B2 A4 B5 B2 B5` | electric-chartreuse×2, deep-vivid-blue, bright-red-orange×2 | "red x2, yellow x2, blue x1" |
| `B9 A4 B9 A4 A8` | bright-lime-green×2, deep-vivid-blue×2, bright-purple-pink | "green x2, blue x2, purple x1" |
| `B1 B9 B5 B1 A2` | strong-golden-yellow×2, bright-lime-green, bright-red-orange, med-royal-blue | "yellowx2, red, green, cyan" |
| `AF B9 AD B3 A8` | bright-golden-yellow, bright-lime-green, neon-magenta, bright-orange, bright-purple-pink | new — 5-distinct-color chase |
| `B9 B1 B6 B1 B6` | bright-lime-green, strong-golden-yellow, bright-cyan, strong-golden-yellow, bright-cyan | new — 3-distinct-color chase |
| `B5 B1 B9 A4 A8` | bright-red-orange, strong-golden-yellow, bright-lime-green, deep-vivid-blue, bright-purple-pink | new — 5-distinct-color chase |
| `B5 B1 A4 B5 B2` | bright-red-orange×2, strong-golden-yellow, deep-vivid-blue, electric-chartreuse | new — mixed-repeat chase |

As with E9 05, expect MagicBand+ and Starlight Wand to render the same color index
differently — the perceived color names in the notes (e.g. "red" for `red-orange`, "purple"
for `bright-pink`) are consistent with known cross-device divergence, not decode errors.

**Flash/solid families (mask `010`/`111`/`100`):** all 9 non-chase samples collected so far
share the same underlying zone-byte pattern in TL/BL/BR (`010` mask), suggesting these three
zones may always move together as a group in this opcode's non-chase behavior, with TR/C
carrying independent state. Needs isolated confirmation — current samples don't vary TL/BL/BR
independently of each other.

### Byte 14 - Unresolved Modifier

**Retracted as sub-mode selector.** Previously theorized as `0x30`=chase / `0xF0`=solid. The
expanded dataset shows:

- Every chase sample (mask=101 all zones) has byte 14 = `0x30`, no exceptions (9/9) — so
  `0x30` does still reliably co-occur with chase, but that's now understood to be downstream
  of the mask pattern, not the cause of the chase behavior.
- Non-chase samples show byte 14 = `0x32`, `0xFC`, `0x14`, or `0x00`, and these do **not**
  cleanly separate into distinct visual behaviors as originally assumed — `0x32` and `0xFC`
  both occurred with the identical `[2,2,2,7,0]` mask/zone pattern but were logged with
  different-looking effects ("cuts on, slowly fades out" vs. "White cuts on, cuts off, ~1.5s" —
  these may in fact be the same behavior described differently, or byte 14 may be doing
  something subtler like flash-count or a hidden variant flag).

Bitwise, the observed values don't share an obvious single flag either:

| Value | Binary | Family seen with |
| --- | --- | --- |
| `0x30` | `0011 0000` | Chase (9/9) |
| `0x32` | `0011 0010` | Flash/solid family B |
| `0xFC` | `1111 1100` | Flash/solid family B |
| `0x14` | `0001 0100` | Flash family A |
| `0x00` | `0000 0000` | Flash/solid family C |

Bit 5 (`0x20`) is set in `0x30`/`0x32`/`0xFC` but not `0x14`/`0x00` — a candidate bit to isolate
in a dedicated sweep, but not yet confirmed to mean anything on its own.

**Sweep result — byte 14 confirmed inert within a fixed mask family.** The Suggested Lab Test
#1 sweep from the prior revision was run (`wand-lab-log-1784773152359.json`): mask/zone colors
and tail held constant at the flash/solid family-B template (`5D 46 5B F0 00`), byte 14 swept
through `0x00, 0x02, 0x10, 0x14, 0x20, 0x32, 0x34, 0xFC` — all 8 logged as identical behavior
("Outer white, inner off/black, steady on, ~24s"). **No visible effect from byte 14 at all**
when mask is held fixed. This resolves the `0x32` vs `0xFC` discrepancy noted above as
observer/description variance between the two originally sparse samples, not a real behavioral
difference — both really are the same effect. Byte 14 is very likely either fully inert, or
gates something not observable from the LED output alone (e.g. an internal animation-family
selector that happens to coincide with mask in every sample collected so far). Treat as safe to
copy verbatim from a template; do not build rule logic that branches on its value.

**Retracted: there is no extra tail byte.** A prior revision of this section claimed the
family-B sweep samples above were 17 bytes as captured (one byte longer than chase-family
packets), and treated that as a real structural difference — a distinct "extra tail byte" at
doc-byte 15, sitting between the modifier and the 3-byte tail. This was wrong. Every sample in
the sweep that produced this finding showed a constant `0xFC` at doc-byte 15 regardless of what
value was actually being swept at doc-byte 14 — that should have been recognized as a sign the
capture batch was corrupted (a duplicated or glitched byte), not evidence of a real field. A
fresh batch of confirmed-working real-world show packets settles it: every family, chase and
flash/solid alike, is 16 bytes as captured (18 doc bytes), with the modifier at doc-byte 14
immediately followed by the same 3-byte tail at doc-bytes 15-17. See the top-of-file byte
diagram (now unified into a single format) and Revision History for the full retraction.

### Bytes 15-17 - Tail

**Chase mode confirmed 3-byte tail.** A full isolation sweep
(`wand-lab-log-1784773152359.json`, chase template `B2A4B5B2B5`, byte14=`0x30`, timing=`0x64`
held constant, only tail bytes varied):

- **Byte 15 confirmed inert** — tested `0x7B` (original), `0xFF`, `0x00`. All three produced
  identical normal 5-color chase behavior, ~13s on-time. Safe to treat as a don't-care byte.
- **Byte 17 confirmed inert** — tested `0xB0` (original), `0xFF`, `0x00`. Same result, no
  behavioral difference. Safe to treat as a don't-care byte.
- **Byte 16 has a confirmed, precisely-bounded anomalous band — not a single odd value.** A
  follow-up sweep (`wand-lab-log-1784775166514.json`, chase template `B2A4B5B2B5`, modifier
  `0x30`, timing `0x64` held constant, byte 16 stepped by `0x08` through `0x48`-`0x78`) resolves
  the boundary precisely and finds **two** distinct non-standard behaviors, not one:

  | Byte 16 range | Behavior | Confirmed by |
  | --- | --- | --- |
  | `0x00`-`0x48` | Normal 5-step uniform chase (TL→BL→BR→TR→C, even timing) | prior sweep + `0x48` this round |
  | `0x50`-`0x60` | **8-step "abnormal chase"** — zone sequence 4,5,1,2,3,4,5,1 repeating | `0x50`, `0x58`, `0x60` (3/3) |
  | `0x68`-`0x78` | **Uneven 5-step chase** — 4 of 5 zones on for ~0.5s, 5th zone on for ~1s | `0x68`, `0x70`, `0x78` (3/3) |
  | `0x80`-`0xFF` | Normal 5-step uniform chase | prior sweep (`0x80`, `0xA0`, `0xC0`, `0xE0`, `0xFF`) |

  This is a fully-bracketed result — every value tested from `0x48` through `0x80` in `0x08`
  steps is accounted for, with no untested gap larger than the sweep's own step size. The
  transition looks like a genuine **numeric-range-gated selector** rather than a bitmask: the
  boundaries (`0x48`/`0x50`, `0x60`/`0x68`, `0x78`/`0x80`) don't correspond to clean single-bit
  flips, but the three bands are each internally consistent across every value tested inside
  them. Whatever this byte actually encodes, treat `0x50`-`0x78` as an "avoid" range for
  standard 5-step chase output until finer sub-banding (if any exists) is investigated.
  Everything below `0x50` and at/above `0x80` is now well-confirmed safe.

**Retracted: there is no extra tail byte in flash/solid mode.** A prior revision of this section
claimed family B carried a 4th tail byte the chase family didn't, "confirmed inert" via a sweep
of `0x00, 0x40, 0x80, 0xC0, 0xFF` (plus the original `0xFC`). This entire finding is wrong and is
retracted — see the top-of-file byte diagram and Revision History. The underlying sweep data
(`wand-lab-log-1784773152359.json`'s byte-14 sweep) was corrupted: every sample in it showed a
constant `0xFC` at what was being called "doc-byte 15," regardless of the value actually being
swept at doc-byte 14 — a telltale sign of a duplicated or glitched byte in the capture, not a
real field holding steady. A batch of confirmed-working real-world show packets (chase and
flash/solid alike, all 16 bytes as captured) settles it: doc-byte 14 is the modifier in both
families, immediately followed by the same 3-byte tail at doc-bytes 15-17, no extra byte
anywhere. The "byte 14 confirmed inert" finding earlier in this doc is unaffected by this
retraction — that sweep's 8 samples, while drawn from the same corrupted batch, were varying the
correct byte (doc-byte 14) and got a real answer (no visible effect); it's specifically the
"there's a 4th byte after it" interpretation that was wrong.

**Chase mode does not tolerate an inserted 17th byte.** Sending a chase packet with a spare
`0x00` byte inserted right after the modifier — i.e. `... 30 00 7B 7D B0` instead of the normal
`... 30 7B 7D B0` — produced the **uneven 5-step pattern** (the `0x68`-`0x78` band behavior
described above), not the standard uniform chase. This test was originally framed as "does chase
tolerate the same extra byte flash/solid mode has" — given that framing is now known to be based
on a false premise (flash/solid mode never had an extra byte), the corrected framing is simpler:
**an out-of-spec 17-byte chase packet does not get silently ignored or gracefully handled; it
produces different, non-standard behavior.** That's still a useful, standalone finding — don't
send malformed-length E9 0C packets and expect graceful degradation. What's still unresolved is
*why* this specific insertion produced the uneven-5-step pattern rather than some other outcome:
under a naive "the device reads a fixed offset for the pattern-selector byte" theory, the
inserted `0x00` would shift what was tail-byte-1 (`0x7B`) into the pattern-selector position, but
`0x7B` sits just outside the confirmed `0x68`-`0x78` uneven-band upper bound — close, but not a
clean match, so a simple offset-shift explanation doesn't fully account for the result on its
own. Only one sample exists for this test; treat "malformed-length chase packets misbehave" as
solid but the specific mechanism as an open, low-priority question.

## Building Your Own

All families use the same packet structure (16 bytes as captured, `E1`/`E2`-prefixed):

```text
<E1|E2> 00 E9 0C 00 <TIMING> 0F <ZONE_TL> <ZONE_BL> <ZONE_BR> <ZONE_TR> <ZONE_C> <MODIFIER> <TAIL x3>
````

### `<TIMING>` (doc byte 7 / rule-config offset 5)

Same formula as [E9 05](./e9-05.md#timing-byte-07): `on_time = 1.5×tval` at scaler=0,
`3.0×tval` at scaler=1, `fade_ms = fade_bits×500`. **Now confirmed reliable in both solid mode
and chase mode** — see Byte 07 section above for the sweep that confirmed this. The
`always_on` bit (bit 7) gates loop-forever vs. bounded-run behavior in chase mode (confirmed in
an earlier revision's dataset, not retested since but nothing here contradicts it).

### `<ZONE_*>` (doc bytes 9-13 / rule-config offsets 7-11)

`zone_byte = (mask << 5) | color_index`. For **chase mode**, mask is `0b101` on all five zones
(`0xA0` base OR'd with your 0-31 color index). For **flash/solid families**, copy the mask
pattern from a matching template below rather than guessing — mask meaning outside chase is
still not independently confirmed (only the specific captured templates are known-good).

**Worked example — chase TopLeft = vivid-blue (index 4):** `(0b101 << 5) | 4 = 0xA4` — matches
confirmed samples above exactly.

### `<MODIFIER>` (doc byte 14 / rule-config offset 12)

**Confirmed inert within the flash/solid family-B mask pattern** (8-value sweep, all identical
output — see Byte 14 section above). Use `0x30` for chase (confirmed 9/9 reliable, though now
believed to be inert too rather than causal). For flash/solid families, any value from the
tested set (`0x00, 0x02, 0x10, 0x14, 0x20, 0x32, 0x34, 0xFC`) is safe; copying verbatim from a
template remains simplest.

### `<TAIL>` (doc bytes 15-17 / rule-config offsets 13-15)

For **chase mode**: bytes 1 and 3 of the tail (doc bytes 15 and 17) are confirmed inert — any
value tested produced identical behavior. **Byte 2 of the tail (doc byte 16) has a confirmed,
precisely-bounded anomalous range** — avoid `0x50`-`0x78` (splits into an 8-step "abnormal
chase" at `0x50`-`0x60` and an uneven-timing 5-step chase at `0x68`-`0x78`, see Bytes 15-17
section above). Everything at `0x48` and below, and `0x80` and above, is confirmed safe. `7B 7D
B0` is a safe known-good default (both `0x7B` and `0xB0` are in confirmed-inert positions).

For **flash/solid families**: not independently swept yet — copy verbatim from a working
captured sample.

## Suggested Lab Tests

Tests #1-3 from an earlier revision (byte-16 `0x60` boundary, the flash/solid "extra byte" that
turned out not to exist, and whether chase tolerates an inserted byte) are resolved — see Bytes
15-17 section above and Revision History for the retraction. Rob has indicated zone-color
isolation (the remaining lower-priority item from further back) isn't needed for his use case,
so it's dropped from this list. Remaining open items:

### 1. Sub-band the two byte-16 anomalies

The `0x50`-`0x60` (8-step) and `0x68`-`0x78` (uneven 5-step) bands are each confirmed only at
`0x08` spacing — the exact transition points (is it `0x4C`/`0x64`/`0x7C`, or somewhere else
within each `0x08` gap?) aren't pinned down, and it's not yet known whether either band has
further internal sub-behavior (e.g. does the 8-step pattern's animation speed or exact sequence
change across `0x50`→`0x58`→`0x60`, or is it identical throughout the band?). Lower priority
than getting the boundary itself confirmed (done) — worth doing only if finer control over
these alternate patterns becomes useful for a show effect.

**Suggested packets** (chase template held constant, `0x04` spacing across each transition):

```
e100e90c0064 0f b2a4b5b2b5 30 7b4cb0   (between confirmed-normal 0x48 and first-abnormal 0x50)
e100e90c0064 0f b2a4b5b2b5 30 7b64b0   (between the two abnormal bands: 0x60 and 0x68)
e100e90c0064 0f b2a4b5b2b5 30 7b7cb0   (between last-uneven 0x78 and confirmed-normal 0x80)
```

### 2. Pin down the inserted-byte mechanism in chase mode (low priority)

One sample showed a chase packet with a byte inserted after the modifier produces the
uneven-5-step pattern rather than being ignored, but the simple "fixed-offset read gets shifted"
theory doesn't cleanly predict that specific result (see Bytes 15-17 section above). Only worth
chasing further if there's a reason to care about _why_ — for the immediate goal of "don't send
17-byte chase packets," the existing single sample is sufficient. If revisited, try inserting
different byte values (not just `0x00`) at the same position to see if the resulting pattern
changes predictably with the inserted value.
